# Workbench Template - Blueprint

## Product Destination

The Workbench Template is a copyable reference installation of LLM Workbench.
It gives a new project a coherent starting structure and gives maintainers a
real installed room in which to verify an explicit harness update. Its files
explain their ownership without pretending to be a separate fictional application.

## People And Problems Served

A person starting a project needs a legible foundation. An arriving agent needs
clear authority, product boundaries and navigable owners. A harness maintainer
needs a reference room whose installed behavior can be checked independently of
the producer checkout. The template serves those needs with the same plain-file
contract that it demonstrates.

## Promised Outcomes

A reader can understand each control, lane and collection, find its owning source,
and distinguish reusable structure from room-specific history. A copy supplies
an understandable starter that can be deliberately adapted to a named product.
An explicit update preserves identity, historical evidence and intentional local
differences while exposing compatibility and unresolved acceptance honestly.

## Desired Experience And Behavior

One local command explains the room. The tour is an orientation aid checked
against the manifest, not a second authority or an application to impose on every
future project. Agents enter through AGENTS and STARTUP, then the assigned Spec
and Task; the Runbook, Architecture and Glossary route needed procedures, owners and meanings. They
preserve the scope of ordinary requests and capture significant fresh context,
decisions and corrections as source-linked Wiki jots before dependent output.
Legacy JSON notes remain readable; a recipient-specific handoff is Markdown.
A specification-only request produces specification work only.

## Integrated System Design

Eight root controls separate behavior, destination, vocabulary, ownership routes,
procedures, work projection and human orientation. The manifest declares installed support paths.
Stable specs retain scoped requirements and evidence; accepted active ADRs retain
architectural decisions, with explicit history views for retired decisions. The
Architecture routes to the complete spec catalog and the room Wiki. The installed
runtime operates locally. Managed core skills are tracked in this room's
`.agents/skills/` lane with a source receipt, beside the optional skills this
room selected; `.claude/skills` is one relative link into that lane. A fresh clone can
recover those files without a provider-home installation, while actual host
invocation remains separately verifiable.

[Template ownership and continuity](workbench/docs/adr/0001-template-ownership-and-continuity.md)
preserves the cross-cutting decisions behind these boundaries.

The optional tour enumerates the actual manifest lanes and collections; its tests
check those names and ownership descriptions. Node.js 20 or newer and built-in
`node:test` keep that orientation runnable without installing dependencies.

## Cross-Cutting Qualities And Constraints

The template carries no application data or secrets. It has tracked and ignored support state:
generic schema examples, durable records and authorized shared
Wiki jots are tracked; explicit private jots, legacy local notes, handoffs and
recovery material remain ignored. Supported lifecycle
operations may seed, migrate, back up or privately synchronize only authorized
state. No secret or personal content belongs in a copyable starter.

The manifest is the path authority. Source and tests establish verified behavior;
controls and assigned owners establish accepted intent. The tour must explain
every manifest lane and collection. Managed runtime changes use explicit updates
with receipts and recovery. Historical provenance remains distinct from installed
source identity; file presence and a successful structural check cannot establish
native behavior, remote delivery or improved agent reliability.

## Desired Lifecycle

The reference can be read and run in place. A named update compares its controls
with the exact reviewed upstream template, preserves deliberate differences and
original evidence, verifies installed tools and ordinary workflows, and obtains
independent review before integration. Publication to main remains owner-controlled.
The reference's prior version history remains accessible through its owning records.

Future product-specific adaptation requires explicit product intent and its own
verification. Updating this reference proves that update only; it does not prove
automated personalization, Genesis or an end-to-end fresh-project workflow.

## Non-Goals

This is not a fictional Example application, an autonomous portfolio manager, a
replacement for upstream tool tests, or a tutorial for designing every product.
It does not require a paid service, private catalog, Foundry machinery or network
access for ordinary local work. It does not publish itself, update unrelated rooms,
import live personal context into copies or claim that every agent obeys every rule.
