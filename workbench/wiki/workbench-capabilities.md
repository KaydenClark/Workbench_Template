# Workbench Feature And Capability Catalog

LLM Workbench gives an agent project a shared operating contract, a path from
ideas to verified delivery, and durable knowledge that survives a conversation.
This reference explains its offered capabilities, their purpose, their limits
and their introduction history. It covers both portable project-room features
and tools maintained only in the upstream Workbench repository.

The reference describes the inspected upstream source at
[`afc68e62`](https://github.com/KaydenClark/LLM_Workbench/tree/afc68e62b1f58174a20c354034e141a766ace89d),
including later development. It is **prepared for v3.2.2**. A copy of this page
does not establish that every listed capability is installed in its host room.
Use the room's `workbench/manifest.json`, managed receipts, Runbook and actual
tool entry points to check availability. Workbench_Template's installed baseline
for this documentation contribution is v3.2.1.

## Reading The Catalog

Each entry says **what it does and why**, the **earliest supported introduction
label**, and where its **source or proof** can be read. Links are pinned to an
upstream commit so this reference works in a fresh project, the source repository
and Workbench_Template without copying upstream delivery records into a room.
Version labels below are source-history evidence; the Version Evidence section
distinguishes historical generations, candidate stamps and release proof.
“Later development” means a capability exists in the inspected source but its
first newly numbered release has not been established.

The page is a substantive product reference. `MEMORY.md` remains the Wiki's single
router; individual feature articles retain their detailed explanations and
historical evidence. Read only the section needed for the current question.

Portable room features are installed or configured through the public setup and
update routes. Producer tools under upstream `tools/`, maintainer skills and
repository-specific interfaces are identified separately. Optional transport,
team and Foundry utilities require their own configuration; ordinary local work
does not depend on them.

## How The Capabilities Fit Together

An idea is explored through saved grilling and confirmed understanding. Settled
direction reaches the Blueprint and decision records; a Spec bounds one
capability, and Tasks cut it into verifiable work. Implementation produces
tests, documentation and recoverable evidence. Assembled review, integration,
owner Human QA and main verification are distinct events. Durable knowledge
returns to the Wiki, and local working context is reconciled before cleanup.

The inspected source also records an evolving open vocabulary of workflow verbs.
The Tracker's existing step labels and the runtime's lifecycle commands retain
their own meanings; this reference does not rename or pretend to implement
every accepted destination design.
## Version Evidence

“Introduced” names the earliest evidenced Workbench generation for the capability described, rather than the date its Wiki article was created. Original behavior, later amendments, integration, release stamping and an installed consumer update are distinct facts. Each row links a source-backed feature capture pinned to the inspected upstream main commit [`afc68e62`](https://github.com/KaydenClark/LLM_Workbench/commit/afc68e62b1f58174a20c354034e141a766ace89d) and a generation proof. This section documents the retained captures; the rest of this catalog covers additional implemented capabilities.

- **v0 through v2.0** are reconstructed historical generations; **v2.1** was the first explicit version stamp. **v2.2** was a local candidate never committed; its work entered v2.3.
- **v3.0.0** was an internal implementation milestone and **v3.1.0** an unreleased candidate. Their introduction labels establish source history, not a published release. The Template’s older replay document calls v3.1.0 public; the canonical source explicitly corrects that claim.
- **v3.1.1–v3.1.4** identify historical generations. The v3.1.4 notepad work was repaired and consolidated into **v3.2.0**; **v3.2.0** has recorded main promotion, separate from its withdrawn later readiness verdict.
- **v3.2.1** is an evidenced candidate stamp. The October 4 release disposition says that candidate was never released. Current main subsequently received October work while retaining that stamp, so the stamp alone cannot date each later capability or prove publication. Later additions are identified as development with commit evidence.
- **v3.2.2** is the owner-requested target for this catalog contribution. This documentation does not itself declare the whole release complete, change a runtime version or satisfy installed-upgrade and release gates.

Sources: [source version policy and lineage](https://github.com/KaydenClark/LLM_Workbench/blob/afc68e62b1f58174a20c354034e141a766ace89d/README.md#versioning-and-upgrades), [v3.2.0 release disposition](https://github.com/KaydenClark/LLM_Workbench/blob/afc68e62b1f58174a20c354034e141a766ace89d/workbench/specs/S-050-workbench-v3-2-0-release/SPEC.md#why-retired), and [v3.2.1 docket disposition](https://github.com/KaydenClark/LLM_Workbench/blob/afc68e62b1f58174a20c354034e141a766ace89d/workbench/specs/S-054-v3-2-1-review-boundary-integrity/SPEC.md#why-retired).

## Maintaining And Reusing This Reference

The owner of a capability change updates its existing explanation and this
reference in the same delivery. Preserve the distinction between an original
capability and a later amendment. Refresh `last_verified` only after checking
the claims that changed, and add a dated History entry naming the authorizing
operation. Do not replace an unknown introduction with the manifest's current
version merely to fill the cell.

Use this entry format for a new row in the relevant section:

```text
Capability: the user-visible name, not just an internal filename or Spec ID.
What and why: observable behavior and the problem it solves.
Availability and limits: portable, optional, producer-only, preview or planned;
  prerequisites, important exclusions and any difference from older installs.
Introduced: earliest evidenced generation or release; for later development,
  say the release is unassigned and cite its introduction commit/date.
Evidence: immutable upstream source/test links and the owning explanation.
```
